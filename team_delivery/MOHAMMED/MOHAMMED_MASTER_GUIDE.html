10. المتطلبات الوظيفية وغير الوظيفية والحالات الحدية لمهام محمد (FR, NFR & Edge Cases)

المهمة المتطلبات الوظيفية (FR) المتطلبات غير الوظيفية (NFR) الحالات الحدية والطرفية (Edge Cases)
TASK-02 & 03 (Protocol & Manager) نماذج Pydantic للغلاف الموحد، وإدارة قنوات اتصالات الغرف (connect, disconnect, broadcast). حجم رسالة لا يتجاوز 4096 بايت، وعزل تام لقنوات الغرف بحيث لا تستلم غرفة رسائل غرفة أخرى. عميل يرسل JSON تالف (Bad JSON)، عميل يرسل رسالة فارغة، بث رسالة لغرفة فارغة بدون مستخدمين.
TASK-04 & 05 (Auth & Events) التحقق من توكن JWT في query param، فحص عضوية الغرفة، وبث أحداث JOIN و LEAVE اللحظية. إغلاق الاتصال غير المصرح فورياً بأكواد قياسية: 4001 (Unauth), 4003 (Forbidden), 4004 (Not Found). توكن منتهي، توكن مزور، مستخدم يحاول الاتصال بغرفة لم ينضم إليها في قاعدة البيانات.
TASK-08 & 09 (Heartbeat & Translation) نبضات كل 30 ثانية، فصل العميل الصامت بعد 90 ثانية، واستدعاء translate_message لكل متلقٍّ. عدم حظر حلقة الأحداث غير المتزامنة (Zero Async Blocking) أثناء الترجمة أو فحص النبضات. عميل ينقطع اتصاله فجأة دون إرسال LEAVE (يتم تنظيفه بالـ Timeout)، تعطل محرك الترجمة (تسليم النص الأصلي).

11. المشاكل والأخطاء الشائعة وكيفية تصحيحها وحلها فوراً (Mohammed Troubleshooting Guide)

🚨 المشكلة 1: خطأ RuntimeError أثناء بث الرسائل (Dictionary changed size during iteration)

السبب: قيام مستخدم بقطع الاتصال في نفس اللحظة التي يقوم فيها الـ Loop بالمرور على قائمة اتصالات الغرفة.

الحل البرمجي السريع: استخدم نسخة سريعة من القائمة عند البث: for ws in list(self.rooms[room_id]): وليس القائمة الأصلية مباشرة.

🚨 المشكلة 2: انهيار السيرفر عند إغلاق العميل للمتصفح فجأة (Unhandled WebSocketDisconnect)

الحل البرمجي السريع: ضع حلقة الاستقبال داخل كتلة try...except WebSocketDisconnect: وقم باستدعاء manager.disconnect(room_id, ws) وبث حدث LEAVE في قسم الـ finally.

🚨 المشكلة 3: تأخر بث الرسائل بسبب انتظار الترجمة (Async Block in Loop)

الحل البرمجي السريع: استخدم asyncio.gather لترجمة وإرسال الرسائل لجميع المستلمين المتصلين بالتوازي بدلاً من حلقة for المتسلسلة البطيئة.

7. الميثاق والدستور الموحد لأعضاء الفريق الأربعة (Unified Team Constitution)

لضمان نجاح دمج المشروع ومنع حدوث أي تعارضات أو أخطاء عند تجميع أعمال الفريق، يلتزم كل عضو بالقواعد الصارمة التالية:

📜 الدستور البرمجي الموحد (The Golden Rules)
  1. عزل الملكية التام (Zero Cross-Editing): ممنوع منعاً باتاً تعديل أي ملف خارج نطاق ملكيتك المحددة. إذا احتجت ميزة من زميلك، استدعِ الدالة المصرح بها ولا تكتب كوده بنفسك.
  2. تجميد العقود الرسمية (Frozen Contracts): لا يحق لأي عضو تغيير أسماء مسارات الـ API أو صيغ رسائل الـ WebSocket أو أسماء حقول قاعدة البيانات دون موافقة كتابية رسمية من قائد المشروع أحمد العماري.
  3. قاعدة الترجمة الحتمية (Identity Rule): يمنع استخدام القيمة "none" نهائياً في أي سياق للترجمة. إذا كانت لغة المصدر هي نفس لغة الهدف، تكون النتيجة دائماً: source_used = "identity" و confidence = 1.0.
  4. حظر الأسرار والـ Hardcoded Keys: ممنوع وضع أي مفتاح سري أو كلمة مرور أو Token داخل ملفات الكود البرمجي؛ كافة الإعدادات تُقرأ من ملف .env حصراً.
  5. قاعدة الـ Stop & Fail: إذا فشل الاختبار في الخطوة 4، لا تنتقل للمهمة التالية أبداً، ولا تخفِ المشكلة، بل أصلح الكود داخل ملفك المخصص حتى يظهر PASSED باللون الأخضر.

8. بروتوكول منع أخطاء التكامل والدمج (Zero-Regression & Merge Policy)

مجال التكامل الالتزام الصارم المطلوب من العضو الخطأ الشائع المحظور قطيعاً
الـ REST API الالتزام بنموذج الاستجابة الموحد data / error وأكواد الحالة (200, 201, 400, 401, 403, 404, 409). تغيير اسم حقل في JSON أو إرجاع كود 200 عند حدوث خطأ.
الـ WebSocket الالتزام بالأنواع الستة فقط (JOIN, LEAVE, TEXT_MESSAGE, TYPING, HEARTBEAT, ERROR) وحجم 4096B. ابتكار نوع رسالة جديد أو تجاوز حد حجم الرسالة المسموح به.
الـ Database استخدام معرفات UUIDv4 لكافة الجداول، وإجراء التعديلات عبر هجرات Alembic حصراً. تعديل الجداول يدوياً في قاعدة البيانات دون كتابة سكريبت Migration.
الـ Frontend حفظ التوكن في localStorage، والتعامل السلس مع حالات التحميل والخطأ وتحديث الواجهة تلقائياً. افتراض استجابة الـ API دائماً دون معالجة حالات الانقطاع أو البطء.
